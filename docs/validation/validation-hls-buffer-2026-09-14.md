# 短 HLS 窗口与延迟解说验证

日期：2026-09-14。环境：Linux、Python 3.14、FFmpeg N-126390-g9fc8c785e2、Tesseract 5.5.0。

## 问题与修复

现场视频源的播放列表仅保留三个四秒分片。双路混流等待较慢的 B 站解说时，视频读取停顿，日志报告跳过三个已过期分片。输出中的视频 PTS 出现约 12.04 秒的相邻包间隔，音频仍连续，表现为画面反复定格。直接读取比赛源能得到完整的四秒分片，单路连续读取也正常。

增加输入的 `thread_queue_size` 无法绕过 FFmpeg 对多个输入的调度。本次为远程 HLS 比赛源增加独立读取进程，通过 FIFO 向混流进程提供 MPEG-TS。队列上限为 4096 个包，不主动丢弃溢出包；原画及原声音轨继续复制，使用 `mpegts_copyts=1` 保留源时间戳。HTTP 头、Cookie 与视频直连设置仍由读取进程使用。

停止和重启会清理两个进程；主混流进程的标准输入用于媒体时，以进程终止信号停止。启动失败和取消也会清理已经启动的输入进程。

## 验证结果

| 范围 | 结果 |
| --- | --- |
| 混流、音量、Supervisor、OCR offset 单元回归 | 121 项通过 |
| 非浏览器真实媒体回归 | 27 项通过 |
| Ruff、格式、Git 差异检查 | 通过 |

新增回归用本机 HTTP 服务提供仅保留最近 1.5 秒的 HLS 播放列表，并提供起始内容更早、按时间发送的解说流。完整输入有 400 帧。测试保存已生成的输出分片，避免正常的播放列表淘汰影响总帧数统计。

- 加载修改前的混流启动方法，同一回归在帧数断言处失败，仅得到 225 帧。
- 使用修复后的实现，400 帧全部保留，最大相邻视频 PTS 间隔为 0.02 秒，首帧像素及音视频相对 PTS 与输入一致。
- 启动失败和启动中取消的回归确认已启动的缓冲输入会被清理。正常完成后，实际输入子进程和诊断线程均结束。
- 既有回归继续验证加密 HLS、Cookie、视频直连与 B 站代理、不同偏移、音频增益、HEVC/fMP4、分片清理及重启流程。

真实媒体测试需要允许本机 HTTP 套接字。新增测试的最终结果是在修正有限音源的结束标记、完整保存输出分片后单独验证；其余 26 项在同轮完整媒体执行中通过。总计为去重后的 148 项。

## 现场对照与限制

独立双路对照保持同一对源及当时的偏移，使用上述缓冲路径运行约 42 秒。FFmpeg 记录输出 729 帧、29.12 秒视频，启动阶段需要等待较慢音源；检查留存的完整分片，视频帧间隔连续为 0.04 秒，完整分片均为两秒。读取进程单独转封装时，抽查的 100 个视频包和 172 个音频包均保留，PTS 变化为零。

最初报错的 OCR 轮次未完整留存，瞬时超时原因未复现。诊断期间原服务已自动恢复复核，两路识别分别约 0.40 秒和 0.26 秒。随后留存的 B 站四帧也通过实际 Tesseract 连续走表验证。本次没有调整 OCR 算法、ROI 或超时预算。

现场对照及本机回归不代表整场、所有源或原生 Windows/macOS 验收。FIFO 以包数限制容量，内存占用随码率和包大小变化，持续超出缓冲容量的源间延迟仍可能阻塞读取。

原运行会话未加载更新；比赛结束后已由用户停止。修复将在下次从本工作区启动 Footboy 时加载，未为验收重新打开已经结束的直播。
