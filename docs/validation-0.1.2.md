## 发现与修复

旧控制页只要 `canPlayType('application/vnd.apple.mpegurl')` 返回非空值就使用原生 HLS。当前 Chromium 会声明支持这种类型，但实播中出现 `PipelineStatus::DEMUXER_ERROR_COULD_NOT_PARSE`，播放器暂停；同时 FFmpeg 仍持续生成可由 FFmpeg 正常解码的 HLS 分片。

现改为：Apple 浏览器保留原生 HLS；其他浏览器在支持 MSE 时使用包内 hls.js，没有 MSE 时才回退到可用的原生 HLS。实播确认 hls.js 正常工作，浏览器持续解码真实画面。两种视口的回归强制模拟“Chromium 声明支持原生 HLS”，检查实际采用 hls.js、播放时间前进以及调整后继续播放；hls.js 的本机 Blob Worker 不再被测试误判为外部下载。

另外，初次解析两房间均返回 HEVC，本机浏览器不支持 HEVC；选择 B 站现有的 H.264 视频线路后继续验证，视频没有转码。采样确认不同编码/线路的源 PTS 起点不同，切换线路后重新采样并设置手动 `D`。测试用初值只负责让两个无关房间进入同一输出时间轴，不衡量赛事内容同步精度；对齐定义继续保持 `D = K_B - K_V`。

## 实播结果

修复后完成两轮流程，分别约 85 秒、182 秒。后者包括偏移、普通退出恢复、停止及再次连接；不是连续 3 分钟无中断的压力测试。

| 检查 | 结果 |
| --- | --- |
| 房间解析、ffprobe 验收、控制页启动 | 通过；两轮从提交连接到实际解码播放约 3–5 秒 |
| 正负方向微调 | `+0.5s`、`−0.5s` 均应用；两轮恢复约 4.2–6.2 秒，包含 1.5 秒合并窗口 |
| 六档连续点击 | `−2s / −0.5s / −0.1s / +0.1s / +0.5s / +2s` 全部操作，合并后回到原偏移并继续播放 |
| 持续播放 | 扩展流程共 12 个 10 秒观察窗口，播放时间各前进 9.834–10.076 秒；窗口之间包含下述恢复操作 |
| 媒体健康 | DTS 异常始终为 0，无页面 JavaScript 异常；各稳定阶段 FFmpeg 速度接近 1× |
| 视频复制 | 同期独立读取输入，匹配 6 个 RGB 像素哈希完全相同的输出关键帧 |
| 音频来源与复制 | 输出剥除 ADTS 封装后匹配 675 个输入 AAC 包；音频可解码且非静音，采样最大 RMS 约 0.204 |
| 源 PTS | 根据相同帧/包比较输入输出时间戳的位移，音频相对视频的额外位移与设定 `D` 的误差约 0.167ms |
| 播放地址与媒体服务 | 复制到剪贴板的地址正确；真实 TS 分片 Range 请求返回 206 和对应的 188 字节 |
| 普通退出恢复 | 主动向本任务的 FFmpeg 发送 `q`，触发普通退出；重新解析 B 站并约 6.1 秒恢复播放 |
| 恢复期间手动优先 | 恢复时新增 `+0.1s`，恢复后保持该值及手动来源标记 |
| 停止、保存、重新连接 | 停止后进程退出、播放列表写入 ENDLIST，控制页仍可用；清空初始偏移后再次连接，复用保存值并持续播放 10 秒，再次停止成功 |
| 桌面与手机尺寸 | 无水平溢出；真实画面、微调、复制地址、停止和再次连接可操作 |

启动时观察到短暂缓冲，hls.js 自动恢复；偏移恢复时间受本轮三秒关键帧间隔和网络条件影响，未声称固定在五秒以内。上述 PTS 精度描述的是媒体封装中的偏移应用误差，不是两个房间内容的同步误差，也不代表音频设备的实际听感验收。
